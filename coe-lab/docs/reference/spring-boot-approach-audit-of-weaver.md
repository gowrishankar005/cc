# Independent audit: Weaver vs. the greenfield "smart Spring Boot → CALM" approach

**Auditor stance:** this audit grades Weaver against the discovery/enrichment matrix derived from `building-calm-from-spring-boot-research.md` (approaches A–F + the layered pipeline + the §5 construct mapping), **as an independent solution-approach auditor** — Weaver's own claims were not trusted. Every verdict below was checked against `pipeline/src` source this session (read-only), not against CLAUDE.md/STATUS.md prose.

**Audit-process finding #0, before any capability row:** the project's own primary documentation (CLAUDE.md) is **materially stale against the code**. It states "the code below doesn't touch Kubernetes manifests at all yet" and "control detection and the k8s-manifest provider don't exist yet" — but `src/scanner/k8s-manifest-provider.ts`, `openapi-provider.ts`, `deployable-manifest-provider.ts`, `cfn-manifest-provider.ts`, `analysis/k8s-trust-pass.ts`, `messaging-pass.ts`, `outbound-http-pass.ts`, `env-soft-graph-pass.ts`, and `modules/calm-generator/system-node-builder.ts` all exist and are wired in. Weaver is **considerably better** than its own top-level docs claim. That's a documentation-integrity risk in its own right (a new contributor or reviewer grading from CLAUDE.md would under-score the platform badly), but for this audit it means: grades below come from source, and several are *higher* than the docs would suggest.

## Ranked findings (what to take away)

1. **A1 — Weaver never reads Spring's own configuration.** The single highest-yield, lowest-cost evidence source for its most important target language is entirely absent: no `application.yml`/`.properties` parsing anywhere. Everything Weaver knows about databases/brokers comes from *code* signals (imports, annotations); one line of `spring.datasource.url` carries the DB technology, host, and protocol that the code lane has to infer or miss. This is also the cheapest big win: a YAML/properties reader is a new scanner provider + catalogue rows, squarely inside the existing "structured-file ingestion" mechanism (same class as the k8s and OpenAPI providers that already exist).
2. **A13 — no runtime verification lane, and nothing planned.** The research doc's core novel idea (Actuator/in-process exporter as a post-resolution oracle, diffs = findings) has no Weaver counterpart. Long-term this is the only way to catch what *all* static lanes are structurally blind to: profiles, conditional beans, placeholder-resolved URLs.
3. **B9 — `protocol` slots exist and are all `null`, including where the value is already knowable** (JDBC on persistence edges). Near-zero-cost fix; verified safe against the 1.3 draft schema despite FINOS's skill claiming deprecation.
4. **A7 — the idiomatic Spring persistence shape (Spring Data repositories) is the explicitly-unimplemented catalogue row**, while the less-common bare-`@Entity` shape is the implemented one.
5. **B3 — grain conflict with FINOS's own rule** (node = deployable unit vs. Weaver's file/class-derived units). Not wrong, but a real divergence from the ecosystem's stated convention that CALM consumers will notice.
6. **Finding #0 — CLAUDE.md/reference-doc staleness**: k8s, OpenAPI, messaging, outbound-HTTP, system-node, and deployed-in are all built but documented as missing. Weaver's audit score is significantly better than its own docs claim; fix the docs before an external reviewer grades from them.

**Overall verdict:** against the greenfield matrix Weaver scores ✅ on 8 of 17 discovery lanes and 6 of 15 construct rows, with its misses concentrated in exactly two themes — **it reads code and deployment manifests but not application configuration (A1–A3), and it has no runtime lane (A13)** — while exceeding the greenfield approach on every governance/honesty dimension (Table 3). The platform's architecture (provider + pass + catalogue) already has the right extension seams for A1 and B9; A13 is the only finding that requires a genuinely new kind of lane.
