# Before building it: does anything already close the Spring-config/build-file/Docker gap?

**Question:** the audit + root-cause docs recommended two new Weaver providers (`spring-config-provider.ts`, `build-manifest-provider.ts`). Before writing either, check whether an existing OSS tool already does this — reuse over reinvention.

**Method:** every candidate below was checked against its **real source** via `gh api` (repo contents + code search), not trusted from a search-engine summary. One candidate's capability claim (cdxgen + Spring config) was directly contradicted by its own source and is corrected here rather than repeated.

---

## Verdict table

|---|---|---|---|---|---|

## Net effect on the remediation plan

This **shrinks the "build from scratch" scope from two new providers to one, real one**, and de-risks the remaining one:

1. **A2 (build files) + A3 (Docker/compose)** — drop the planned `build-manifest-provider.ts`. Reuse `cdxgen` instead: shell out (Node-to-Node, no new runtime class), parse its CycloneDX output for dependency names (persistence/messaging corroboration) and container/compose service facts. Less code, more correct, actively maintained by someone else.
2. **A1 (Spring config) — still needs a genuine new Weaver provider**, because nothing found in this research reaches `application.yml`/`.properties` deterministically without either a JVM bridge (OpenRewrite) or a build/jar-read (Spring's own metadata). But it's no longer a from-scratch vocabulary guess: **`spring-config-provider.ts`'s target key list (`spring.datasource.url`, `spring.kafka.bootstrap-servers`, `spring.data.redis.*`, …) should be derived from `rewrite-spring`'s recipe catalogue** (read the recipes for the key names and profile-resolution rules they already encode) rather than reconstructed from memory or guesswork — reuse of *knowledge*, even where reuse of *code* isn't architecturally clean.

This keeps the "smallest change, most unlock" framing from the original audit intact, just cheaper: one new deterministic Weaver provider instead of two, plus one new shelled-out dependency (`cdxgen`, already in the right runtime) instead of hand-written pom.xml/Dockerfile parsers.
