# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working principles (Karpathy-inspired, adapted for this project)

Four behavioral principles, derived from [Andrej Karpathy's observations on LLM coding pitfalls](https://x.com/karpathy/status/2015883857489522876) (via [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)) and merged here with what this project's own history has already shown works. These apply on top of everything else in this file, not instead of it.

**1. Think Before Coding — don't assume, don't hide confusion, surface tradeoffs.**
This project has paid for silent assumptions before: "populating `controls` with a placeholder `requirement-url` is still schema-valid CALM" (`requirements v0.10 §0`) was a reasonable-sounding claim that turned out false the moment `calm validate` actually ran against it — `calm-cli` does a live host-allowlist check no one had verified. "Graphify isn't installed in this environment" was stated as settled fact across multiple sessions before someone actually tried `pip install` again and found it already there, just not on `PATH`. Neither was caught by re-reading the design — both were caught by running the real thing. **State assumptions explicitly and verify them against the real tool/schema/repo before asserting they hold — "specified" and "true" are different claims, and this codebase's own comments (`x-aac-scope-limitations`, "left out honestly rather than stubbed to look complete") exist because that distinction was hard-won.** When a genuine decision point has more than one defensible answer and only the user can pick (build-environment assumptions, scope tradeoffs, which of several correct designs to build) — ask, the way the four locked decisions before `Architecture_as_Code_Java_Solution_Design.md` did, rather than picking silently and finding out later it was the wrong branch to build on.

**2. Simplicity First — minimum code that solves the problem, nothing speculative.**
The three construct-mapping catalogues (`node-type-mapping.yml`, `relationship-type-mapping.yml`, `control-requirement-catalogue.yml`) exist specifically so builders stay thin and new capability is a data row, not new code — that discipline is *why* six real bugs this session were each a small, targeted fix (a regex, a missing field, a hardcoded default) rather than a rewrite. If a new signal needs more than a catalogue row plus one of the four already-proven mechanisms (native typing, decorator extraction, import-detection, structured-file ingestion), that's a real signal to stop and ask whether it's actually in scope before inventing a fifth mechanism, not a reason to quietly build one. No speculative config/flexibility beyond what an evidenced requirement calls for — matches `v0.6 §1.5`'s own stopping rule: new discoveries go in the backlog table, they don't become active work just because they were noticed.

**3. Surgical Changes — touch only what you must, clean up only your own mess.**
Every builder (`node-builder.ts`, `interface-builder.ts`, `relationship-builder.ts`, `metadata-builder.ts`, `control-builder.ts`) is isolated on purpose — fixing one should never require touching another. When `build-calm.ts` was split into builders, the old monolithic logic was fully removed because it was being *replaced*, not left dangling next to its replacement; conversely, `decorator-builder.ts`/the k8s-manifest provider are *not* stubbed out just to make the builder list look complete — they're honestly absent because nothing upstream feeds them yet. Match that: when a fix is scoped to one mechanism (the `findRule` word-boundary regex fix touched exactly `findRule`, nothing in `signal-mapper.ts` or the catalogues), keep it there. Remove only what your own change makes unused; leave pre-existing gaps named, not silently patched over or silently deleted.

**4. Goal-Driven Execution — define success criteria, loop until verified.**
This is the pattern that actually found every real bug this session: every change was framed as "does the BoA/NestJS/Fineract regression suite still produce the same counts, does `calm validate` return 0 errors, does the output match grep-verified ground truth" — never "does this code look right." Before a non-trivial change, state the verify step first: *"add JAX-RS route composition → verify: 19/19 real Fineract routes match grep-verified source"*, not just "add JAX-RS route composition." For multi-step build work, state a plan with a verify per step before starting — the way the four-task list (Graphify, Override-apply, control-builder, Java coverage) did this session, each closed only once its own regression check passed, not once the code compiled.

## What this repository is

Working artefacts plus a real, running codebase for a deterministic **Architecture-as-Code (AaC) pipeline** that extracts structure from a real, polyglot (Java + Node + Python) monorepo and generates CALM 1.2 JSON. There is explicitly **no LLM in the core generation path** — this is enforced architecturally, not just stated (see `pipeline/` below).

**`pipeline/`** is a real Node.js/TypeScript project — Slice 1 of the vertical-slice delivery strategy (requirements v0.6 §1.5), implementing a CodeGraph + Graphify hybrid scanner. Build/run:
```
cd pipeline && npm install && npm run build
node dist/orchestration/run-slice.js <package-root> [<package-root> ...] --out <dir>
npm run validate -- <dir>/architecture.calm.json -f pretty   # real FINOS calm-cli schema validation
```
Verified end-to-end against real Bank of Anthos Flask services (`spikes/boa/repo/src/accounts/userservice`, `contacts`) — see "Pipeline architecture" below for what's actually built and what was empirically found while building it.

Read `docs/spikes/Claude_Code_Handoff_Brief.md` first for the project's research history; read the "Pipeline architecture" section below for the current codebase.

## Critical technical findings to not re-litigate

These were established by actually running the tools against real repos — treat them as settled unless you re-run the same tests. **The first item below is a correction**: the spike docs' "no bulk export" finding was true for the CodeGraph version tested at the time, but is now stale against the currently-installed version — read `docs/requirements/CALM_Generator_Requirements_v0.1.md` §5 for the current picture, not just the spike docs in isolation.

- **CodeGraph now ships a public, typed, documented SDK with real bulk export** (`CodeGraph` class, `QueryBuilder.getAllNodes()`, `getOutgoingEdges()`/`getIncomingEdges()`, plus a no-persistence-needed `extractFromSource(filePath, source)` — confirmed present in `dist/index.d.ts` of the installed v1.5.0). The older "no bulk export, must query undocumented internal SQLite" finding in `docs/spikes/CodeGraph_vs_Graphify_Comparison.md` / `CodeGraph_Discovery_Spike_Report.md` no longer reflects the installed tool version.
- **CORRECTION — `Node.decorators?: string[]` is NOT a reliable generic annotation hook for Java.** An earlier pass in this project inferred otherwise from reading extraction source alone; that inference was tested and falsified — see `docs/spikes/CodeGraph_Annotation_Extraction_Reconciliation_Spike.md`. Real result against Fineract's `ChargesApiResource`/`Charge`: `node.decorators` came back `undefined` for every genuinely-annotated class/method (it's populated only for java.js's hardcoded Lombok-synthesis special case). Persisted `decorates` **edges** were also empty (0/0) in a small single-module index — resolution has nothing to fuzzy-match external annotation types against at that scale. **The reliable extraction point is `CodeGraph.extractFromSource(filePath, source)`'s raw `unresolvedReferences`, filtered to `referenceKind === 'decorates'`** — this reads correct annotation names (`Path`, `GET`, `Entity`, `Column`, …) with correct `fromNodeId` attribution, independent of indexing/persistence/resolution succeeding. Build the Annotation Interpretation Layer against this, not against `node.decorators` or persisted edges.
- **CodeGraph's Java framework support is still Spring/Play-only** (unchanged from the spikes — confirmed by reading `resolution/frameworks/index.js` in the current version). JAX-RS (`@Path`/`@GET`) is real production code in enterprise Java (confirmed via Fineract — `fineract-charge/.../ChargesApiResource.java`) and is extractable via the `extractFromSource()` approach above, never typed as `route`. An **Annotation/Decorator Interpretation Layer** is still a required new component, not "thin config."
- **CodeGraph's `detect()` gate is root-relative and fails silently.** In monorepos with per-package manifests (common in Python), indexing from the wrong root produces zero routes with no warning — indistinguishable from "this codebase doesn't use the framework." This is a **cross-language** requirement, not Python-specific. Always verify non-zero `route` counts per package after indexing, not just once per run.
- **LIVE BUG, not yet fixed — `pipeline/src/modules/calm-generator/build-calm.ts` generates an invalid `interacts` relationship shape.** It emits `{interacts: {source, destination}}`; the real CALM 1.2 schema (`core.json#/defs/interacts-type`, confirmed against real usage in FINOS's own `calm-3.json`) requires `{interacts: {actor: <node id>, nodes: [<node id>, ...]}}` — an actor node fanning out to the nodes it uses, not a pairwise edge. `{source, destination}` is `connects`'s shape, and `connects` is the correct default for essentially every relationship this pipeline generates (real FINOS files use `connects` even for in-process, non-network delegation — it's not strictly "network connections"). The bug hasn't been caught by `calm validate` because every relationship generated so far has been a service→database edge, which already routes to `connects` by luck of the existing `isDbEdge` check — it will fire the moment a service-to-service relationship exists, which the still-unbuilt Kubernetes trust-relationship layer (`docs/requirements/CALM_Generator_Requirements_v0_7.md` §3) is about to produce. Fix scoped, not yet applied — see `docs/requirements/CALM_Generator_Requirements_v0_9.md` §1.
- **`node-type` and interface `type` are NOT closed enums** — confirmed from the authoritative schema (`core.json`: `node-type-definition` is `anyOf[enum, string]`; `interface.json`: `interface-type` is `{unique-id}` + `additionalProperties: true`, `type` isn't even a named schema property, purely convention). The enum lists in calm.finos.org's prose pages are the *common* set, not the *only valid* set — real production files (`calm-3.json`) use informal types like `"api"` that aren't in that list at all. This is real headroom for staying language/framework-agnostic: new node-types or interface-types can be introduced as new signal sources are added without any schema-compatibility risk.
- **CodeGraph cannot merge multiple indexed roots into one queryable graph** (GitHub Issue #281, closed as not planned). **Superseded by an actual build decision** (see "Pipeline architecture" below): Graphify runs as the cross-package structural backbone instead of a from-scratch FQN-stitcher — Graphify has no per-root `detect()` gate, so it captures cross-root edges natively. This is adopted and built for Slice 1, not backlog — Slice 1's scale (one/two small packages) never approaches Fineract's 7,062-file scale, the only case where Graphify timed out. jQAssistant-for-Java (Option A) is still deferred to Slice 2 and untestable in this environment (no JVM/Maven/Docker). See `docs/requirements/CALM_Generator_Requirements_v0_6.md` §4 for the requirements-doc-era framing (now superseded by the pipeline build) and `pipeline/src/analysis/cross_package/graphify-reconciler.ts` for the actual mechanism.
- **Delivery strategy pivot (v0.6 §1.5): vertical slices, not broad coverage.** Slice 1 = one real package from the actual target monorepo (not a proxy repo), Python or Node only (FastAPI/Flask/NestJS), no Java. Slice 2 = Java, later — scope widened in v0.12 beyond v0.6's original "Spring MVC + JAX-RS + JPA only": now includes Quarkus (JAX-RS detection transfers unchanged; CDI bootstrap markers need their own catalogue rows) and the Spring Data repository-interface persistence pattern (`@Repository extends CrudRepository`, distinct from bare `@Entity`) as real, evidenced additions — not just the original three. Spring Batch (real banking EOD/batch-job pattern) and JMS/ActiveMQ are evidenced backlog, not built. Everything else (WebFlux, RabbitMQ, MyBatis, gRPC, Django/SQLAlchemy, TypeORM/Prisma, infra-manifest enrichment, OpenAPI ingestion, jQAssistant, Graphify-as-primary-backbone) is explicit backlog — deferred, not discarded, but not active work unless it blocks Slice 1/2's specific scope.
- **JPA (`@Entity`) persistence signals are missed entirely by CodeGraph's native typing** — not even as fuzzy edges, confirmed again this session against both Fineract and Bank of Anthos. Persistence detection needs its own pass via `extractFromSource()`'s `decorates` refs for `Entity`/`Table`/`Column` (same mechanism as JAX-RS above, not `node.decorators`).
- **Python's framework-resolver roster has grown** since the original spikes: `flaskResolver`/`djangoResolver` are now registered alongside `fastapiResolver` (confirmed by reading `resolution/frameworks/python.js` in the current version) — the spikes only tested FastAPI. Note: a quick side-check found `extractFromSource()` on a bare single Python file (no project manifest/context) produces zero `decorates` refs and zero native route nodes — the Java-annotation-extraction shortcut above does not substitute for a full per-package index when framework-native route typing is what's needed.
- This project's own methodology caught a real drift: the jQAssistant hybrid-tool idea was explored early on, dropped by omission (not a reasoned rejection) once work moved to CodeGraph-only, and only resurfaced in v0.4 after being reconnected to the cross-package edge problem above. Worth remembering when a tool/approach silently stops being mentioned — that's not the same as it having been ruled out.

## Pipeline architecture (`pipeline/`)

**Status note:** this section describes what's built as of requirements v0.6's scope (HTTP routes, persistence, cross-package structural edges). `docs/requirements/CALM_Generator_Requirements_v0_7.md` §3 specifies a Kubernetes-manifest signal layer (trust relationships from shared Secrets, deployment decorators) that is **not yet implemented** — the code below doesn't touch Kubernetes manifests at all yet. Don't assume auth/trust relationships are captured just because persistence relationships are; check `pipeline/src/scanner/` for a k8s-manifest provider before trusting either way.

Four layers per requirements v0.6 §1: Scanner → Rules → Analysis → Orchestration → Modules, with `typed-facts.json` (`pipeline/src/types/typed-facts.ts`) as the fixed contract between Analysis and any downstream module. `calm-generator` is the first and only module built.

**Dual-engine scanner, each tool doing what it's verified good at (not one deferred behind the other):**
- **CodeGraph** (`scanner/codegraph-provider.ts`) — per-package indexing, native `route` typing where its resolver covers the framework, plus `extractFromSource()`-based decorator facts (the resolved mechanism, requirements v0.6 §5).
- **Graphify** (`scanner/graphify-provider.ts`) — one pass across all package roots given to a run (`graphify extract <root> --code-only --no-cluster`, real output confirmed at `<root>/graphify-out/graph.json` after actually running it, not assumed from the flag name), used only as the **cross-package structural backbone** — it has no per-root `detect()` gate, so cross-package edges are captured natively instead of needing to be reconstructed. `analysis/cross_package/graphify-reconciler.ts` maps Graphify's flat/kind-less nodes onto CodeGraph-typed units (filePath + line-range match) and promotes cross-root edges to `crossPackage: true` relationships. This **replaces** a from-scratch FQN-stitcher (the originally-planned v0.6 §4 Option B) — Graphify already does that job.
- Both are real dependencies now (`@colbymchenry/codegraph` npm, `graphifyy` pip) — this is an adopted decision for Slice 1, not the "Option C, backlog, unverified" status the requirements doc still shows; Slice 1's scale (one or two small packages) never approaches the scale where Graphify's one known weakness (timeout on Fineract's full 7,062-file repo) would bite.
- **`analysis/cross_package/persistence-detector.ts`** — CodeGraph gives zero persistence signal for any language tested so far (Java JPA, now confirmed Python SQLAlchemy too), but Graphify's raw `imports_from`/`contains` edges already carry it for free. Detects a file importing a known persistence library (sqlalchemy, psycopg2, pymongo, …), finds the class Graphify says that file `contains`, and emits it as a `database`-kind `TypedUnit`. Found and fixed by actually auditing generated CALM output against real source (`db.py`'s `UserDb`/`ContactsDb` classes were completely invisible before this existed) — don't assume persistence is out of reach just because CodeGraph doesn't provide it; check what Graphify's raw edges already contain before building new extraction.

**Hybrid rule layer — LLM-assisted rule *authoring*, never rule *application*:** `rules/signal-catalogue.yml` is the versioned, human-owned rule table the deterministic pipeline reads (implements `docs/spikes/Gap_Closure_Build_Ready_Specs_v0.1.md` §4's `signal-catalogue.yml`). `rules/suggest-rules.ts` is a **separate, offline, explicitly-invoked** CLI — never imported by `orchestration/run-slice.ts` or anything in its call graph — that calls an LLM (if `ANTHROPIC_API_KEY` is set; otherwise it reports what it would have proposed and exits) to propose new catalogue entries from signals `signal-mapper.ts` logged as unmapped. It writes only `rules/proposed-updates.json`, a draft; a human manually promotes entries into `signal-catalogue.yml`. This is how "no LLM in the core generation path" and "LLM can update detection/extraction rules" both hold at once — verify this boundary before changing either file.

**Real findings from building and running this, not assumed:**
- Native route extraction works exactly as expected: 4/4 grep-verified routes recovered for both `userservice.py` and `contacts.py`.
- **New correction, not previously known:** `extractFromSource()`'s `decorates`-ref extraction — verified working for Java (Fineract, see the reconciliation spike) — returns **zero** results for Python's `@app.route(...)` decorators, even with full project context (a properly-opened `CodeGraph.open()` on the real package root, not the earlier "missing context" theory). This is a genuine language-specific gap in CodeGraph's generic decorator-collection path, not a bug in this pipeline. Native route typing fully covers Slice 1's Flask/FastAPI/NestJS needs regardless, so this hasn't blocked anything — but don't assume the decorator-fact fallback works for Python without re-verifying.
- `graphify extract <root> --code-only --no-cluster --out <dir>` writes to `<dir>/graphify-out/graph.json` (confirmed by running it, not inferred from `--help`). Real output shape: nodes have `{id, label, file_type, source_file, source_location}` — no `kind` field, confirming `docs/spikes/CodeGraph_vs_Graphify_Comparison.md` §5. `source_location` is a single-line string (`"L19"`), not a range.
