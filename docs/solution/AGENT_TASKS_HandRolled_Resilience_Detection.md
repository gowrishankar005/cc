## Real evidence pass — done, not assumed

Searched `spikes/` for `Thread.sleep` (Java's hand-rolled retry/backoff primitive) outside test code. Found real, non-trivial hits in **two independent real repos**:

1. **`spikes/fineract/repo/fineract-provider/.../gcm/domain/Sender.java`** — a genuine, textbook hand-rolled exponential-backoff retry implementation, confirmed by reading the real code: explicit `attempt`/`backoff`/`retries`/`BACKOFF_INITIAL_DELAY`/`MAX_BACKOFF_DELAY` variables, `backoff *= 2` doubling, and the method's own javadoc literally states "this method uses exponential back-off to retry in case of service unavailability." The `Thread.sleep` call itself sits inside a small private `sleep()` helper method, called from the retry loop in a different method of the same file — this pipeline's one-unit-per-file granularity still correctly attributes the signal to the right file.
2. **`spikes/boa/repo/src/ledger/balancereader/.../LedgerReader.java`** (and two sibling copies in `transactionhistory`/`ledgermonolith`) — a real `while(alive) { try { Thread.sleep(pollMs); } catch (InterruptedException e) {...} ...}` shape, but this is a **polling loop**, not a retry-on-failure pattern. **Real, important finding**: the same bare "loop + try/catch + sleep" shape covers at least two genuinely different real intents (retry-with-backoff vs. periodic polling) that deterministic matching cannot tell apart — exactly the ambiguity BACKLOG.md's own framing anticipated an LLM would need to resolve, now confirmed with real code, not assumed.
3. Two more real, unconfirmed candidates found in the same search (`AbandonedConnectionCleanupShutdownListener.java`, `StuckJobExecutorServiceImpl.java`) — plausible but not read in detail; real material for the verification step below, not hand-picked to look good.

**No real Python (`time.sleep`) or Node/TS evidence found in any `spikes/` repo.** Scope this task to **Java `Thread.sleep` only** — do not add Python/Node signals speculatively; a future evidence pass can extend this the same way `imageEngine()`/messaging detection were extended incrementally, not by guessing ahead of evidence.

## Real design finding — this must NOT create a phantom TypedUnit

Traced precisely, not assumed: `signal-mapper.ts`'s `mapSignalsToUnits` gives EVERY file with ANY matched signal a real unit, defaulting to `kind: 'service'` when no entry-point/persistence/messaging category is present (`signal-mapper.ts` ~line 258). A `Thread.sleep` call-site signal routed through the normal `signal-catalogue.yml`/`matchSource: call` mechanism (the one every other call-site row in this project uses) would, if weighted `>= CONFIDENCE_FLOOR` (40), **manufacture a phantom "service" node for any file that happens to call `Thread.sleep` for an unrelated reason** (a shutdown-delay, a test wait, a UI-adjacent pause) — a real, serious false-positive risk this task must design against, not discover after shipping. If weighted low enough to be safe (matching `python-jwt-decode-call`'s existing 20/corroboration-only precedent), the signal alone never crosses `CONFIDENCE_FLOOR` and **the actual strongest real evidence found above (`Sender.java`, a plain unannotated class with zero other typed evidence) never becomes a unit at all** — the mechanism would find nothing for its own best real example.

**Resolution: don't route this through `signal-catalogue.yml`/`mapSignalsToUnits` at all.** Build a small, dedicated, purpose-built detector — same architectural pattern `outbound-http-detector.ts`/`env-soft-graph-detector.ts` already use for evidence-thin signals that must never fabricate a construct: it emits a real, prefixed `IgnoredItem` directly, **never a `TypedUnit`, regardless of what else the file does or doesn't have**. This sidesteps the phantom-node question entirely by construction, and needs no new extraction mechanism: `raw.callFacts` (a `CallFact[]`, already extracted once per file via `codegraph-provider.ts`'s `extractCallFacts()`, already consumed by `signal-mapper.ts`'s own call loop at `passes.ts` ~line 54) already carries every real call site's `referenceName`/`filePath`/`line` — this task's detector reads the SAME already-extracted array, no second CodeGraph invocation.
