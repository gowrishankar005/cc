## Real scoping findings — this is NOT a simple wire-up like T-1 was

Two real gaps found scoping this, neither obvious from §3.3's prose alone:

1. **Every existing residual/card/schema path is keyed to a `unitId`, never a relationship id.** §3.3 needs a `relationship_remove` Override on reject, which targets a relationship's own CALM `unique-id` (confirmed: `TypedRelationship.id` is reused directly as the CALM `unique-id` by `relationship-builder.ts`) — but nothing in `residuals.json`'s schema, `ReviewQueueItem`, or `cards.py` currently has anywhere to put a relationship id as a first-class field. **Resolution: don't add one.** The existing free-text `rationale` convention (already used by every other producer to embed a bridge id, a ConfigMap key/value, etc. — see `tier-b-single-candidate`'s own detail string) is sufficient: embed the relationship's real `id` directly in the rationale text, and set `unitIds: [rel.from, rel.to]` (both are real, already-existing units) so baseline-carry-forward, bulk-apply sibling-grouping, and consequence-ranking all keep working unchanged. No schema change needed for this part. **Disclosed edge case, not fixed**: two distinct low-confidence relationships between the exact same unit pair would share one `(trigger, unitIds)` baseline signature — rare, name it in a code comment, don't design around a case with no real instance.
2. **`env-soft-graph-detector.ts`'s emitted relationships carry zero evidence today.** The resolved-relationship push (`env-soft-graph-detector.ts`, after `seenPairs.add(pairKey)`) sets only `{from, to, kind: 'connects', crossPackage, source: 'k8s', confidence: 20, status, id}` — the literal ConfigMap name/key/basename that produced it (available in-scope at that exact point in the loop as `configMapName`/`keyName`/`basename`/`target.name`) is discarded. Without it, the new residual's card can't show "the literal evidence that produced it," which §3.3 explicitly requires. **Resolution**: add `TypedRelationship.evidenceNote?: string` — a small, additive optional field (tier (b), `Contract_Evolution_Policy.md` §2(b), no `CONTRACT_VERSION` bump), same precedent as the existing `confidence?`/`grade?`/`mechanism?` fields, set only by `env-soft-graph-detector.ts` today; every other producer leaves it unset. **Disclosed simplification**: `seenPairs` dedupes multiple ConfigMap keys correlating to the same unit pair into one edge — `evidenceNote` reflects only the FIRST key that produced it, matching the existing "one edge, not one per key" comment already in that file. Not a bug, name it in the new field's own doc comment.

## Non-negotiable constraints

- **No new mechanism for "confirm."** A confirm decision is a Decision Record with `final_decision: {"action": "accepted", "new_value": null}` and **no Override file at all** — this is already the documented, most-common real outcome (`pack.py`'s own `_render_agents_md`, "Decision Record with NO override"). Do not invent a new override type or a new confirm-specific mechanism.
- **`relationship_remove` needs zero new code** — `override-applier.ts` and `validate_drafts.py` already fully support it (confirmed: `target_type: 'relationship'` is already a valid enum value, `target_ref` already validated against real CALM relationship `unique-id`s). This task only needs to make the relationship's own id citable from the pack.
- **`env-soft-graph-detector.ts`'s existing `--enable-env-soft-graph` opt-in gate is untouched** — the new residual producer is naturally inert when that flag isn't set (no low-confidence relationships exist in `facts.relationships` at all), same "always-on block, naturally a no-op absent evidence" pattern already used elsewhere. Don't add a second gate.
- **`undefined` confidence must never be treated as low-confidence** — `coverage-report.ts`'s own documented convention is "no confidence claim, not zero." The filter is `rel.confidence !== undefined && rel.confidence < CONFIDENCE_FLOOR`, never a bare `rel.confidence < CONFIDENCE_FLOOR` (which would incorrectly fire on every relationship with no confidence claim at all, since `undefined < 40` is `false` in JS but relying on that coercion instead of an explicit check is exactly the kind of implicit behavior this repo's own discipline avoids).
- **`pipeline/scripts/check-residual-taxonomy-sync.js` must pass** — since this diff touches `triage.py`'s `_TRIGGER_MAP`, it requires `Architect_Residual_Review_Session.md` to change in the same diff. §3.1 already has a note anticipating this ("A third kind of producer, not yet built (§3.3)") — turn that into a real producer-table row once built, matching the `silenceFlags`/`IgnoredItem.reason` table format above it.
