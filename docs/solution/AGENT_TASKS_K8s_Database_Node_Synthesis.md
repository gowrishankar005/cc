**Governance/DoD:** `docs/solution/Architecture_as_Code_Solution_Design_v2.md` §5.7a (the design this file executes), `docs/solution/Catalogue_Intake.md` (this is new detection coverage — evidence + test + `BACKLOG.md` entry required, though the evidence bar is largely already met by reusing an already-shipped, already-evidenced mechanism — see below)
**Priority:** #2 in the 2026-09-02 consolidated LLM-assist planning list (despite the name, this specific item is 100% deterministic — grouped with the LLM-assist batch only because it was found in the same review pass).
**Why this file exists:** confirmed real, not hypothetical — a live scan found several services' own `env-soft-graph` evidence (a ConfigMap value naming a database's k8s Service/Deployment) correlates correctly, but `findUnitForDeployment` still fails because the database Deployment (e.g. `ledger-db`) is a pure init-script/Postgres directory with **no scanned source at all** — no `TypedUnit` exists for it, regardless of how well the ConfigMap value resolves.

## Real scoping finding — this needs almost no new code

**Do not build a new database-image catalogue.** `pipeline/src/analysis/cross_package/contradiction-detector.ts` already has exactly this mechanism, shipped and battle-tested: `export function imageEngine(image: string): string | undefined` — parses a real Docker image reference (handles registry ports, multi-segment official images like `mcr.microsoft.com/mssql/server`, tag stripping) and returns a canonical engine name (`postgresql`, `mysql`, `mariadb`, `mongodb`, `redis`, `cassandra`, `oracle`, `sqlserver`, `db2`, `sqlite`, `h2`, `dynamodb`) via its own `ENGINE_ALIASES` map, or `undefined` for an unrecognized image (never guessed). Two real bugs in image-reference parsing were already found and fixed in that function (2026-08-16) — reusing it means this task inherits that correctness for free instead of re-deriving it. **Import and reuse `imageEngine` directly; do not write a second image-parsing function or a new YAML catalogue.**

This mirrors an already-proven precedent exactly: `k8s-namespace-node-builder.ts` already builds a real CALM node directly from k8s manifest evidence (no `TypedUnit`), for a `deployed-in` relationship's synthetic namespace-id target — same "no source file, build the CALM node directly" pattern, same build-order constraint (must run before `relationship-builder.ts`, since a `TypedRelationship.to` has to already be a real node id or `buildRelationships`' own `nodeIds.has(r.to)` filter silently drops it).

## What you're building

1. **`pipeline/src/analysis/cross_package/env-soft-graph-detector.ts`** — in `detectEnvSoftGraphRelationships`, split the current combined `if (!referencerUnit || !targetUnit)` check (the referencer side stays exactly as-is — a referencer with no scanned source is a different, out-of-scope case). For the target side specifically, when `findUnitForDeployment` returns `undefined`, check `target.image` (already a real, already-scanned field on `DeploymentManifest` — `image?: string`) via `imageEngine(target.image)`. If it resolves to a known engine, synthesize the relationship's `to` as a new deterministic id (`k8sDatabaseNodeId(target.name)`, exported from the new builder below — see #2) instead of requiring a real `TypedUnit`; set `crossPackage: true` (a synthesized cross-boundary node has no real `filePath` to compare against); keep `confidence: 20` unchanged (same fixed ceiling every env-soft-graph edge already carries — no reason to differentiate). Only when NEITHER a real `TypedUnit` NOR a recognized database image exists does this fall through to the existing `unresolved-env-target` ignored-item (update its detail text to say so precisely — "no TypedUnit matches... and its deployment image ... does not match a known database engine", not the old "no code-level unit" wording alone, since that's no longer the only failure reason). Also set `evidenceNote` on the synthesized-target relationship (built this session for §3.3) citing the real image match, e.g. `` `ConfigMap "${configMapName}" key "${keyName}" name-correlated to deployment "${target.name}" (image "${target.image}", recognized database engine "${engine}", no scanned source — synthesized k8s-evidenced database node)` ``.
2. **New file `pipeline/src/modules/calm-generator/k8s-database-node-builder.ts`** — mirror `k8s-namespace-node-builder.ts` exactly in structure and doc-comment style: `K8S_DATABASE_ID_PREFIX = 'k8s-database:'`, `k8sDatabaseNodeId(deploymentName): string`, `buildK8sDatabaseNodes(relationships: TypedRelationship[]): CalmNode[]` — scans `relationships` for any `from`/`to` starting with the prefix (check both, unlike the namespace builder which only checks `to` — a referencer will never carry this prefix in practice, but checking both costs nothing and avoids a latent gap if that ever changes), emits one `{'unique-id': k8sDatabaseNodeId(name), 'node-type': 'database', name, description}` per unique deployment name found. Deliberately built DIRECTLY (not routed through `node-type-mapping.yml`'s catalogue) — same reasoning `k8s-namespace-node-builder.ts` already documents: there's no `TypedUnit`/`kind` to route through a catalogue in the first place.
3. **`pipeline/src/modules/calm-generator/build-calm.ts`** — wire in `buildK8sDatabaseNodes(facts.relationships)` at the exact same call-site cluster as `buildK8sNamespaceNodes`/`buildCrossRepoNodes` (before `attachInterfaces`/`buildRelationships`, same build-order comment already there — copy it, don't just add a bare call).

## Non-negotiable constraints

- **Reuse `imageEngine`, never fork it.** Export it from `contradiction-detector.ts` if not already exported (check first — it may already be `export`ed for its own module's tests). Two independent copies of Docker image-reference parsing is exactly the kind of drift this project's own `jdbc-url.ts` consolidation (cited in `contradiction-detector.ts`'s own doc comments) was built to prevent.
- **Only the target side of an env-soft-graph correlation may synthesize a node.** The referencer side keeps requiring a real `TypedUnit` — a service with literally no scanned source is a nonsensical, out-of-scope case, not something this task should also start guessing at.
- **`k8s-database-node-builder.ts` must run before `relationship-builder.ts`** (same constraint `k8s-namespace-node-builder.ts` already documents and enforces via call order in `build-calm.ts`) — verify by checking that a synthesized database node actually appears in `calm.nodes` before asserting the relationship connecting to it validates.
- **No change to `findUnitForDeployment` itself.** It's called from two other places today (`env-soft-graph-detector.ts`'s referencer-side lookup, and `hitl-review-trigger.ts`'s `unresolved-outbound-target` producer shipped this session) — both expect a real `TypedUnit | undefined` return. Don't widen its contract; add the image-matching fallback as new, separate logic in `env-soft-graph-detector.ts` only.
- **A real, existing regression test will need real, re-measured numbers, not guessed ones.** `pipeline/test/regression.test.js`'s `'Deployment correlation — Java Controller-class naming resolves via normalize+substring...'` test (gated on `spikes/boa`, real ledger+accounts services) currently asserts `coverage.relationshipsBySource.k8s === 5 + 6 + 6` and `coverage.unresolvedByMechanism['unresolved-env-target'] > 0` — this is the EXACT real fixture with the EXACT real `ledger-db`/`accounts-db` Postgres-init-script-only deployments this task is designed for. Once this task ships, some of those previously-unresolved correlations will very likely now resolve into real `connects` edges to a synthesized database node, changing both numbers. **Do not guess the new numbers — re-run the real scan and update the assertions to match what actually happens**, per this project's own "verify against the real tool/repo" discipline. If the counts DON'T change, that's also real information (say why in a comment, don't silently leave the old numbers unexplained).
