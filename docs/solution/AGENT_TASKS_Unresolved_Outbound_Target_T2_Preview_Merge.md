# AGENT TASK — §3.2 T-2: canonical-plus-drafts preview/merge tool

**Lane:** Independent — no dependency on any other item in the 2026-09-02 LLM-assist batch. Depends only on T-1 (shipped) existing so there's something real to preview.
**Governance/DoD:** `docs/solution/Architect_Residual_Review_Session.md` §3.2's own "New, and not yet built" bullet (the design this file executes), `docs/solution/AGENT_TASKS_Unresolved_Outbound_Target.md`'s own T-2 note.
**Why this file exists:** §3.2's own text: "canonical `architecture.calm.json` plus the current `drafts/` directory's pending `relationship_add` overrides, rendered as one merged CALM document with drafted-but-unconfirmed relationships tagged distinctly... so an architect can see the *complete*, semantically-marked picture before confirming anything, not just a text list of pending drafts. Read-only, never touches the canonical file or `drafts/` itself." Named as a real gap since §3.2 was designed, never built.

## Real mechanism reuse — do not build a second CALM-merge implementation

**`apply.py` already does almost exactly this**, minus the "preview" part: it merges `drafts/decisions/` + `drafts/overrides/` (via its own already-tested `_merge_drafts` helper — **import and reuse it directly**, don't re-copy its logic) into one temp dir, then shells out to `node dist/orchestration/run-slice.js --from-facts <typed-facts.json> --overrides <tmp-dir> --out <out-dir>` — the exact same code path (`override-applier.ts`'s real `applyOverrides`) a genuine apply uses. **This task's entire mechanism is: run that exact same command, but pointed at a throwaway temp `--out` directory instead of the real one, then diff the result against the real canonical file to find what's new.** No new merge/apply logic — reuse, not reimplement.

## Real correctness finding — the real apply path's own tagging would be misleading if reused unmodified

Traced precisely: `override-applier.ts`'s `relationship_add` case (confirmed reading the real code) unconditionally tags every newly-added relationship with `x-aac-status: reviewed` and `x-aac-override-provenance` metadata, via `withReviewedStatus` — correct and true for a REAL apply, but **would be a false claim in a preview run**: nothing was actually reviewed/confirmed yet, this is a dry-run. §3.2's own design text already anticipated needing a distinct tag (`x-aac-draft: true`, "deliberately not a `FactStatus`/`x-aac-status` value") — this is precisely why: reusing the real apply path's own metadata unmodified would silently mislabel a preview-only relationship as already-reviewed. **This task must strip `x-aac-status`/`x-aac-override-provenance` from any relationship it identifies as a genuine pending draft (see below) and replace them with `x-aac-draft: true`** — never leave the misleading real-apply tags in a preview document.

## Real finding — `drafts/` accumulates everything ever drafted, including already-applied overrides; a naive "is it in drafts/" check is wrong

Traced precisely: `apply.py` never moves, archives, or deletes a draft after successfully applying it — `drafts/decisions/`/`drafts/overrides/` keeps growing across every draft/apply cycle in a session's history. **This means "does an override for this residual exist in `drafts/`" is NOT a reliable signal for "not yet applied"** — an override could already be reflected in the real canonical `architecture.calm.json` from an earlier `apply.py` run, while its own draft file still physically sits in `drafts/`. **The only correct way to identify a genuinely PENDING draft is a diff**: run the full merge (drafts/ against typed-facts.json) into a temp output, then compare its relationship `unique-id` set against the REAL current canonical file's own relationship set (read via the session's own `manifest.json`'s `outDir`, same field `apply.py` itself already reads) — any relationship present in the merged temp output but **absent** from the real canonical file is a genuine, still-pending draft. Anything present in both is either an original canonical fact or an already-applied override, and must be rendered exactly as the canonical file already has it, with no draft tag.

## What you're building

**New file `tools/review-session/preview_merge.py`** (a new, standalone script — matches the existing one-script-per-concern convention: `apply.py`, `draft_tier_b.py`, `bulk_apply.py`, `queue_rank.py`; NOT a new `pack.py` flag, since this is run on-demand, independently, typically after a batch of Tier B drafts exist but before `apply.py` is run for real):

1. Read `manifest.json` for `outDir` (same pattern `apply.py` already uses) and the real canonical `architecture.calm.json` at `<outDir>/architecture.calm.json`.
2. `import _merge_drafts from apply` (reuse directly), merge `drafts/decisions/`+`drafts/overrides/` into a temp dir.
3. Shell out to the SAME `node dist/orchestration/run-slice.js --from-facts <typed-facts.json> --overrides <tmp-dir> --out <preview-tmp-out-dir>` command `apply.py` already builds (reuse the exact argument shape, minus `--strict-overrides` by default) — `<preview-tmp-out-dir>` is a NEW `tempfile.TemporaryDirectory`, never the session's real `outDir`.
4. Read the resulting `<preview-tmp-out-dir>/architecture.calm.json`. Diff its `relationships[].unique-id` set against the real canonical file's own set (loaded in step 1).
5. For every relationship whose `unique-id` is in the merged-temp output but NOT in the real canonical set: strip `x-aac-status`/`x-aac-override-provenance` from its `metadata` array (the real-apply-only tags — see the correctness finding above) and add `{"key": "x-aac-draft", "value": true}` instead.
6. Write the resulting document — real canonical nodes/relationships, plus the newly-tagged pending-draft relationships, nothing else changed — to a clearly-named new file, e.g. `<session_dir>/preview-merged.calm.json`. **Never write to `<outDir>/architecture.calm.json` or anywhere under `drafts/`.**
7. Print a short, real summary (count of pending drafts found, their `unique-id`s) — matching `apply.py`'s own `[apply] ...` console-output convention.

## Non-negotiable constraints

- **Read-only over the canonical file and `drafts/`, always.** Every write goes to the new preview output file or the throwaway temp dir only.
- **Scoped to `relationship_add`-sourced new relationships, matching §3.2's own stated scope — not every override type.** `drafts/` may also contain `node_add`/`node_remove`/`relationship_remove`/`type_change`/`boundary_change` overrides from OTHER residual classes (e.g. `low-confidence-emitted-relationship`'s own reject path). The same `--from-facts --overrides` merge will apply ALL of them (that's `override-applier.ts`'s own real, correct, unconditional behavior — don't try to filter the merge itself). **Disclose explicitly, in this task's own doc update, that non-`relationship_add` effects (a node disappearing, a relationship being removed) will be reflected in the merged output but not specially tagged** — a real, named scope limitation, not silently expanded to handle in this task. A future task can extend the tagging logic if that's ever needed.
- **Never reimplement `override-applier.ts`'s merge logic in Python.** Every construct in the preview document must come from the real `run-slice.js --from-facts` invocation, not a hand-rolled Python-side simulation of what an override would do.
- **Verify the diff baseline is trustworthy before trusting it**: a zero-overrides sanity run (same `--from-facts` command with an EMPTY overrides dir) must reproduce a relationship-`unique-id` set identical to the real canonical file's own set. If it doesn't, the diff-based approach is unsound and the mismatch must be investigated and disclosed, not silently worked around.
