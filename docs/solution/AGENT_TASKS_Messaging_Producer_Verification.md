**Why this file exists:** `messaging-detection-catalogue.yml`'s `typed-field-producer` strategy types a `KafkaTemplate`-typed field as a real messaging producer (weight 40, "sufficient alone" tier) purely from its declaration — deliberately NOT paired with a `.send()`/`.publish()` call-site check, since that would need cross-referencing two different `extractFromSource()` reference kinds within one file, a real mechanism this pipeline hasn't built. **Real finding confirmed while scoping this task, not previously stated anywhere**: unlike `S2-http-without-security-control` (the closest analogous gap), **zero review path exists for this today** — no `silenceFlags` entry, no `hitl-review-trigger.ts` block, nothing in `Architect_Residual_Review_Session.md` §3.1's producer table. ## Real scoping findings — the eligibility question BACKLOG.md flagged as open is resolved

**BACKLOG.md's own caveat says "no cheap deterministic pre-filter exists yet to bound which units are worth asking about."** Checked directly against the catalogue and `Evidence.source` union: **no stronger corroborating evidence source for `category: 'messaging'` exists in this pipeline at all** — only `'field-type'` (the `KafkaTemplate` strategy) and `'graphify-import'` (the SQS/SNS import-only strategy) ever set `category: 'messaging'`. `dependency-manifest` corroboration (the SBOM-based tier) can attach to a messaging unit too, but it only corroborates "this package is really a project dependency" — it says nothing about whether the specific field/import is ever exercised via `.send()`/`.publish()`. **The eligibility filter is therefore trivial and cheap: every `topic`-kind `TypedUnit` is eligible, full stop** — not because there's no way to narrow it, but because no possible narrowing signal exists yet for this specific question. The real, still-open cost concern is call VOLUME at scale in a large repo (T-1's own measured $0.08–$0.32/call), not eligibility correctness — a concern the existing opt-in `--with-dossier` flag and this project's own established per-run cost posture already handle, not something this task needs to solve freshly.

## Non-negotiable constraints

- **No new mechanism for "confirm."** Same as `low-confidence-emitted-relationship`'s own precedent — a Decision Record with no Override (`final_decision: {"action": "accepted", "new_value": null}`) is already the documented, most-common real outcome.
- **`node_remove` needs zero new code** — already fully supported by `override-applier.ts` (including cascading relationship cleanup) and `validate_drafts.py`. This task only needs to make the unit's real id citable from the pack (already true — `unitIds` carries it, same as every other trigger).
- **Do not build the call-site-corroboration mechanism itself in this task.** That's the actual, larger, currently-unbuilt mechanism (`messaging-detection-catalogue.yml`'s own text: "a real mechanism this pipeline hasn't built"). This task is scoped to REVIEW visibility (T-1) and LLM-assisted judgment (T-2) for the gap as it exists today, not to close the underlying detection gap deterministically — that would be a different, larger, separately-scoped task if ever pursued.
- **`pipeline/scripts/check-residual-taxonomy-sync.js` must pass** — T-1's diff touches both `coverage-report.ts`'s `silenceFlags` and `triage.py`'s `_TRIGGER_MAP`, so `Architect_Residual_Review_Session.md` §3.1 must change in the same diff.
