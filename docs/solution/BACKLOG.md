## P1 — Correctness and coverage gaps

| **CodeGraph unit extraction degrades under repeated same-process invocation** | Found 2026-08-13 investigating a Fineract regression-test count mismatch (94 vs 60). A fresh, isolated `node dist/orchestration/run-slice.js` process against `fineract-core` alone gives 94 relationships deterministically across repeated cold runs — the raw Graphify structural graph is byte-identical each time (8553 nodes/21277 edges). Invoking the same scan repeatedly via `execFileSync` from within one long-lived Node process (this pipeline's own regression-test harness shape) instead gives a lower but internally-consistent count (60-64 observed) — same raw Graphify graph, but fewer nodes resolve to a CodeGraph-typed unit. CodeGraph's own per-invocation extraction silently returns fewer units under repeated same-process load, no error or warning surfaced. Not root-caused (closed-source SDK; candidate causes include an internal timeout/budget or memory/fd contention across repeated spawns) — `pipeline/test/regression.test.js`'s fineract-core R0/R2b test was hardened to assert a floor instead of an exact count as an immediate mitigation, but the underlying silent degradation is real and undiagnosed. **Cuts against this pipeline's core "deterministic" claim under this one specific condition** (repeated same-process invocation, not the normal single-invocation `run-slice` product usage) — worth its own investigation before this pipeline is ever run as a long-lived service rather than a per-invocation CLI. |
| **Tier-B residual detection** *(converges with the extension's status-vocabulary work — same gap, independently identified)* | The residual-review tooling can present a "medium-confidence, needs a human decision" card, but no detector currently produces that class of input — every real detection today is either high-confidence (auto-emitted) or too ambiguous to rank (multiple candidates). A detector that separates "one high-confidence candidate just under the auto-emit threshold" from "genuinely many candidates" would give the review tooling real input to act on. |
| **JDBC read-service-vs-table-owner ambiguity — remains a documented limitation, not yet a scoped fix** | Already a named, disclosed limitation (`persistence-import-vs-ownership-ambiguous` in `scope-limitations.yml`); Phase A investigated further (`soln/bug3-jdbc-ownership-phase-a-memo.md`) and found no reliable, corroborated signal: `RowMapper<T>` presence is FALSIFIED as a distinguishing signal (present on the flagship false-positive class itself, `ChargeReadPlatformServiceImpl`, and on 55% of JdbcTemplate-importing files overall — doesn't separate real owners from read-only query services); a bare `@Service`/`@Component` stereotype does NOT already exclude a class either (confirmed via `JournalEntryRunningBalanceUpdateServiceImpl`, `@Service`-annotated and still typed `database`); a naming convention (`*ReadPlatformServiceImpl`) is single-repo-sourced, not corroborated. **Constraint for any future attempt**: `ChargeReadPlatformServiceImpl` has no other mechanism giving it unit existence at all — `Claim_Register.md`'s gold-scored `R2-multi-root-access-terminal` row depends on it resolving to a unit; a fix must only ever change `kind` from `database` to `service`, never suppress unit creation, or it regresses that claim. **Candidate approach identified but not yet tested (2026-08-13): `docs/solution/Engine_Capability_Research_Java_SpringBoot_JAXRS.md` §4.3 — every falsified signal above (`RowMapper`, stereotype presence, naming) is presence-based; the real distinguishing fact is behavioral (does this class actually execute a query through the client it imports, or only wire it through). That's what real data-flow/taint analysis answers and presence-based AST matching structurally cannot — CodeQL's Java data-flow library is the first tool this project has access to that could plausibly resolve this. Untested hypothesis, not a result. **Second, independent real-repo instance found 2026-08-13 while building T-LR-2 against Waltz**: `LegalEntityRelationshipKindService` (a `service`-named class, real import-only persistence evidence, weight 20) resolves as the terminal store of a real direct-delegate chain (`BulkUploadLegalEntityRelationshipEndpoint -> [bridge] -> LegalEntityRelationshipKindService`) — the same false-positive class as `ChargeReadPlatformServiceImpl`, now confirmed in a second, structurally different codebase (Fineract's JAX-RS/JDBC vs Waltz's Spark-routing/jOOQ), corroborating that this isn't a Fineract-specific naming quirk.** |
| **Possible bare-identifier collision inside multi-hop bridge detection — NOT YET REPRODUCED** | Flagged by review of the stereotype-name-collision fix (`graphify-reconciler.ts`'s `isBareNameCollision`), not independently confirmed with real evidence. `multi-hop-bridge-detector.ts` walks the same raw Graphify `imports`/`references` edges via its own separate loop, using the identical bare-label-only node resolution the collision bug is rooted in — but its bridge-candidacy gate (`if (nodeToUnit.has(bridgeNodeId)) continue`) requires the target to have ZERO existing units, which the evidenced collision shape (`Component`/`Response`, both real `@Entity` classes with existing units) structurally cannot satisfy — so the fixed mechanism's exact evidenced shape cannot reach this path. A theoretically-reachable variant (a bare-name collision landing on a genuinely zero-unit interface that is itself `implements`-ed elsewhere by a real persistence/messaging unit) has not been reproduced against a real repo. Needs its own real-evidence pass before scoping a fix, per this project's own discipline — do not extend the collision check here speculatively. |
| **Exception classes mistaken for multi-hop bridge candidates** | Found verifying T-LR-3's real regression against a reference Java/JAX-RS banking platform's charge module: `ChargeRepositoryWrapper` (a real, bare-`@Service` class T-LR-3's new catalogue row correctly makes visible as a bridge SOURCE for the first time) references two real, in-repo exception classes it throws (`ChargeIsNotActiveException`, `ChargeNotFoundException`) — both produce zero TypedUnits (correctly — an exception isn't an architectural unit), pass `isRealBridgeCandidate` (they're real, in-repo files, not external/annotation noise), and so are examined as bridge candidates and honestly refused (0 implementers) rather than fabricated. Not a fabrication bug — no relationship is emitted — but real, avoidable noise in `ignoredItems`: this pipeline's own architectural-bridge concept was never meant to cover a class's own exception-throwing, only its service-layer dependencies. Pre-existing gap in `multi-hop-bridge-detector.ts`'s `isRealBridgeCandidate` (it excludes annotation-type/out-of-root noise but not exception-shaped references), newly SURFACED (not introduced) by T-LR-3 making previously-invisible real service classes into bridge sources for the first time — any future catalogue addition that makes a new class visible as a bridge source could surface the same latent noise. Candidate fix needs its own evidence pass before building (a structural signal — e.g. the reference target's own `extends` edge existing at all, distinguishing a concrete class in an inheritance hierarchy from a bare marker interface — not a name-suffix heuristic, which `OOS-sample-repo-detectors`/this file's own design note already forbid for this exact detector). |
| **Weak-service-unit / messaging-unit duplicate-node risk** | Found while fixing T-LR-3's real regression (a bare-`@Service` class that also genuinely imports a persistence driver was silently losing its `database` classification — fixed via `overridableServiceFilePaths`, a replace-not-duplicate merge in `detectPersistencePass`). `detectMessagingPass` has the identical class of exposure and was NOT fixed: it never calls `existingServiceFilePaths`/`overridableServiceFilePaths` at all, relying only on TypedUnit.id collision to merge with an earlier pass's unit — which never fires against a decorator-created service unit (different id scheme, `file::ClassName` vs `file`). A real class carrying a bare `@Service` stereotype AND real messaging-client import evidence (e.g. a `KafkaTemplate`-typed field) would produce two separate CALM nodes for one real file today. No real fixture has been found exercising this exact combination yet — disclosed in `scope-limitations.yml`'s `weak-service-unit-messaging-collision`, not silently left unnoted. |
| **Bare-implementer-list collision, T-LR-3's stereotype-disambiguation branch** | `multi-hop-bridge-detector.ts`'s new `r2-stereotype` branch is the first mechanism in this file to actively PICK a winner from the raw `implementers` list rather than only ever refusing under ambiguity — re-assessed against the EXISTING \"Possible bare-identifier collision inside multi-hop bridge detection\" row below (same file, same underlying `isBareNameCollision` gap) and found NOT covered by that row's own reasoning: that reasoning is about the bridge TARGET (structurally unreachable, since a bridge candidate requires zero existing units), not the IMPLEMENTER list this new branch walks. Two real, differently-packaged classes sharing one bare name could theoretically cause Graphify's bare-label node resolution to misattribute an `implements` edge, inflating a bridge's real implementer count. Not reproduced against real data (2026-08-16 real-repo verification found no such case) — a real evidence pass is the correct next step if this is ever observed, not a speculative fix now. See `scope-limitations.yml`'s `bare-implementer-list-collision-not-reproduced`. |
| **Bulk residual-decision authoring** | The residual-review UI suggests answering once and applying the decision to a whole class of similar residuals, but no such batch mechanism exists — every residual currently needs its own individually-authored decision record. | **Contradiction detection between evidence sources** | Two sources asserting *different values* for the same fact currently both add weight in `confidence-scorer.ts` — contradiction raises confidence instead of lowering it. Evidenced class: a stale deployment manifest naming one datastore engine while current compose/config name another. Proposal: detect conflicting assertions, force a review status, never average. **E5 (T-P0-6, `docs/solution/E5-confidence-replay-experiment.md`, 2026-08-14) replayed the OTHER half of this row's own combination question (probabilistic-OR vs. summed weight) offline against 617 real units and reported negative — 22 real band changes found, all reviewed as LESS correct (undercounts genuinely-correlated multi-clause evidence from one declaration). Contradiction detection itself still could not be replayed at all — no mechanism to replay exists — so this row remains open and unevidenced on its own actual claim; only the sibling combination-formula question has now been tested and deprioritised.** |
| **Secondary sources may introduce facts, not only corroborate** | Dependency-manifest corroboration is explicitly "never a primary detection source" — correct as a confidence rule, but it means a source that sees something the structural engines cannot is mute rather than low-confidence. | **Bean-factory / stereotype-free wiring detection** | A common real convention — components wired via `@Configuration`/`@Bean` factory methods with no class-level stereotype annotation on the implementation — produces zero detection signal today. **CodeQL DI-resolution experiment run 2026-08-13, positive (`docs/solution/E1b-codeql-di-resolution-experiment.md`): resolves the exact real evidenced case (`ChargesApiResource.readPlatformService -> ChargeReadPlatformService -> ChargeReadPlatformServiceImpl`, via the real `ChargeConfiguration` `@Bean`-factory "starter" class, no stereotype anywhere) — 774 of 2106 total real DI bindings resolved this way, whole-codebase scale, not tuned to Charge.** **T-LR-4 design session (2026-08-15) confirmed, via a direct empirical probe (not assumed), why this needs CodeQL specifically and can't be built as a T-LR-3-style catalogue-row-plus-existing-mechanism fix**: neither of this pipeline's two structural engines captures a method body's `new X(...)` instantiation expression at all — probed directly against a synthetic `@Configuration`/`@Bean` fixture before concluding this, not inferred from reading code. CodeGraph's `extractFromSource()` reports only the `@Configuration`/`@Bean` decorators and the method's declared return type (the interface, not the impl); its persisted index has zero `call`/`constructor`/`instantiation`-kind nodes for the file at all. Graphify's AST pass produces the identical shape — a `references` edge to the return-type interface, nothing referencing the concrete implementation class anywhere in its graph. This is a genuine mechanism gap, not a catalogue gap (`CLAUDE.md`'s "Bug fixes are capability work" / Simplicity First discipline: a new signal needing more than a catalogue row plus a proven extraction mechanism must stop before building) — the only mechanism this pipeline has evidence resolves this shape is CodeQL's data-flow analysis (E1b), and wiring that in live is T-LR-5's own explicit scope, not a quick addition here. This row stays open until T-LR-5 ships or a different, evidenced extraction path is found. |
| **Isolated-node completeness flag (`S6`)** | No check today flags a node with zero real architecture relationships (a node that exists but connects to nothing). Not a schema-validity question — CALM's schema has no concept of it, and `calm validate` can't check it. Same mechanism class as `S1`/`S2`/`S5` in `coverage-report.ts`, at finer grain: per-node rather than per-run. **Must exclude the synthetic `system`-node `composed-of` edge from the "has a relationship" count** (`system-node-builder.ts`) — that edge is structural bookkeeping, not evidence the node participates in any real architecture, and including it would make the flag pass on almost every node in almost every run. Verified compatible with the `lib-fintech-common` must-not-detect trap: that trap resolves by emitting zero nodes, not a lone one. Naming: use `S6`, not "orphan" — that term is already the Decision-Record/Override term for a stale target reference (`override-applier.ts`); reusing it would create ambiguity. **Open question, not yet decided:** soft flag by default (reviewer decides, same posture as S1/S2/S5) with an optional `--strict-isolated-nodes`-style gate (precedent: `--strict-detect`), or a hard gate from the start — lean soft, since a lone node is sometimes honestly correct (a newly-detected unit whose relationships haven't been recovered yet) and hard-failing would punish partial detection rather than reward it. |
| **Mechanical bug-fix generalization check** | `Catalogue_Intake.md` already named a CI check (grep a diff for new catalogue rows lacking test/claim-cell/scope-limitations updates) as "a reasonable escalation if drift is ever observed in practice — not built ahead of that need." **That trigger has now been hit for real, and by the more concerning route: T-LR-1's first pass hardcoded the annotation name `'Configuration'` as a literal, and passive review did not catch it — the project owner found the diff suspicious and had to explicitly task a dedicated review before it was refactored.** Nothing in the existing process (task DoD checklist, the agent's own status report, `Catalogue_Intake.md`'s written rule) caught it on its own; a human had to notice. | **CodeQL `StructuralEngine` integration — checklist, not yet started** | Two real, measured capability gaps evidenced (`E1-codeql-engine-evaluation.md`: 7 real command-bus dispatch edges; `E1b-codeql-di-resolution-experiment.md`: 2106 real DI-resolution bindings, both Fineract-only). **T-P0-2a licensing (committed summary in `AGENT_TASKS_Ext_P0_Experiments.md`, full memo only in gitignored `soln/`):** free CodeQL is OSS-eval only; production/private use needs GHAS. Tracked as `T-LR-5`/`AGENT_TASKS_Ext_Layered_Recovery.md`, which carries the full 7-item checklist: (1) generic detector, no sample-repo names, at full `OOS-sample-repo-detectors` force; (2) build-lifecycle failure degrades like `graphifyy`'s absence already does, never a hard crash; (3) CI/Docker cost resolved, not deferred (flagged since the P0 lane file, still open); (4) claim triple named on report, with the same fabrication-suspicion standing caution as E2's `E-charge-single-L2` landmine; (5) trust tier earned via `T-LR-6`, never automatically primary; (6) a second real-repo instance (`spikes/waltz/repo`, already present, already confirmed structurally different DI convention) before either capability counts as a mechanism-class fix; (7) an explicit scope decision on which capability (or both) this task actually ships, so it doesn't silently grow to cover everything CodeQL has been shown capable of. |
| **Per-(engine, fact-type) trust tiers** | `engine-capability-matrix.yml` routes per (language, framework) and is load-and-log only. Proposal: extend to an evidence-earned trust ranking *per fact type*, so an engine can be primary for one fact class and unranked for another, with the ranking changing as measurements accumulate rather than being config-declared. Prerequisite for adding any engine as a genuine second source. **This is `T-LR-6`'s own prerequisite, in the row above — the same open item, referenced from both directions.** |
| **Fact identity, incremental merge, and review history** | Every run rebuilds facts; Decision Records persist human corrections across runs but individual facts carry no stable identity or status history. Proposal: content-derived identity from semantic coordinates (never file:line, which moves), merge against prior state, and retain who/when/on-what-evidence a status changed. Enables continuous construction and auditability. **Contract change — see `Contract_Evolution_Policy.md`; bumping the contract silently skips any module whose declared major version wasn't bumped with it.** |
| **Cross-repo relationship resolution (beyond co-scanned roots)** | Multi-root covers repos scanned together. Repos *not* co-scanned have no join path. Proposal: a small per-repo manifest declaring the repo's own node ids and published contracts, resolved in strict reliability order (shared API spec identity → published artifact coordinates → service-catalogue/DNS → human review). Never infer a cross-repo edge from naming alone. |
| **Emission-coverage reporting as a governed rule** | `coverage`/`unmapped` reports exist; the rule that a fact silently lost at emission is a defect is not stated as a contract. Proposal: make "what the representation could not carry, and why" a required emission output, so representation portability becomes a measurable number rather than an assertion. |
| **Reviewer-assistance layer (advisory, off the generation path)** | `hitl-review-trigger.ts` produces a review queue; nothing helps a human *resolve* a queued item. Proposal: an advisory layer that explains evidence, proposes hypotheses for flagged unknowns, and drafts catalogue-rule candidates — **never writing facts**, consistent with `OOS-llm-core-path`, which is a permanent non-goal with revisit trigger "Never". Candidate facts surface only in the review queue; on acceptance they are recorded as the human's claim. |
| **Scope-limitations ↔ claim-register consistency** | Ongoing discipline: every new detection gap named in generated-output metadata should have a matching completeness-claim entry, checked each time scope changes. |
