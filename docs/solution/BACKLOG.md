## P1 — Correctness and coverage gaps

| Item | Description |
|---|---|
| **CodeGraph unit extraction degrades under repeated same-process invocation** | Found 2026-08-13 investigating a Fineract regression-test count mismatch (94 vs 60). A fresh, isolated `node dist/orchestration/run-slice.js` process against `fineract-core` alone gives 94 relationships deterministically across repeated cold runs — the raw Graphify structural graph is byte-identical each time (8553 nodes/21277 edges). Invoking the same scan repeatedly via `execFileSync` from within one long-lived Node process (this pipeline's own regression-test harness shape) instead gives a lower but internally-consistent count (60-64 observed) — same raw Graphify graph, but fewer nodes resolve to a CodeGraph-typed unit. CodeGraph's own per-invocation extraction silently returns fewer units under repeated same-process load, no error or warning surfaced. Not root-caused (closed-source SDK; candidate causes include an internal timeout/budget or memory/fd contention across repeated spawns) — `pipeline/test/regression.test.js`'s fineract-core R0/R2b test was hardened to assert a floor instead of an exact count as an immediate mitigation, but the underlying silent degradation is real and undiagnosed. **Cuts against this pipeline's core "deterministic" claim under this one specific condition** (repeated same-process invocation, not the normal single-invocation `run-slice` product usage) — worth its own investigation before this pipeline is ever run as a long-lived service rather than a per-invocation CLI. |
| **Tier-B residual detection** *(converges with the extension's status-vocabulary work — same gap, independently identified)* | The residual-review tooling can present a "medium-confidence, needs a human decision" card, but no detector currently produces that class of input — every real detection today is either high-confidence (auto-emitted) or too ambiguous to rank (multiple candidates). A detector that separates "one high-confidence candidate just under the auto-emit threshold" from "genuinely many candidates" would give the review tooling real input to act on. |
| **`@Configuration` classes mis-typed `database` via driver-import evidence** | Evidenced during Bug 3's Phase A evidence pass (`soln/bug3-jdbc-ownership-phase-a-memo.md`): a `@Configuration`/`@Bean`-wiring class referencing a driver-import library only as a factory-method parameter type (never actually querying with it) is architecturally never a table owner, regardless of which library. Real evidence: 35 of 156 real Fineract files importing `org.springframework.jdbc.core` are `@Configuration` classes (e.g. `AccountingJournalEntryConfiguration`). Cheap, general, ready-to-implement fix — same class of mechanism as the existing annotation read-back (`class-ownership-resolver.ts`), generalizes past JDBC to any driver-import catalogue library. |
| **JDBC read-service-vs-table-owner ambiguity — remains a documented limitation, not yet a scoped fix** | Already a named, disclosed limitation (`persistence-import-vs-ownership-ambiguous` in `scope-limitations.yml`); Phase A investigated further (`soln/bug3-jdbc-ownership-phase-a-memo.md`) and found no reliable, corroborated signal: `RowMapper<T>` presence is FALSIFIED as a distinguishing signal (present on the flagship false-positive class itself, `ChargeReadPlatformServiceImpl`, and on 55% of JdbcTemplate-importing files overall — doesn't separate real owners from read-only query services); a bare `@Service`/`@Component` stereotype does NOT already exclude a class either (confirmed via `JournalEntryRunningBalanceUpdateServiceImpl`, `@Service`-annotated and still typed `database`); a naming convention (`*ReadPlatformServiceImpl`) is single-repo-sourced, not corroborated. **Constraint for any future attempt**: `ChargeReadPlatformServiceImpl` has no other mechanism giving it unit existence at all — `Claim_Register.md`'s gold-scored `R2-multi-root-access-terminal` row depends on it resolving to a unit; a fix must only ever change `kind` from `database` to `service`, never suppress unit creation, or it regresses that claim. |
| **Direct-delegate bridge detection** | Multi-hop architecture-bridge detection currently requires an `implements` edge between a candidate bridge class and its interface. A common real pattern — a concrete service class referenced directly, with no interface at all, that itself imports exactly one persistence/messaging unit — is invisible to the current detector. Real evidence exists (28 real candidates found in a public sample, 0 resolved); not yet built. |
| **Possible bare-identifier collision inside multi-hop bridge detection — NOT YET REPRODUCED** | Flagged by review of the stereotype-name-collision fix (`graphify-reconciler.ts`'s `isBareNameCollision`), not independently confirmed with real evidence. `multi-hop-bridge-detector.ts` walks the same raw Graphify `imports`/`references` edges via its own separate loop, using the identical bare-label-only node resolution the collision bug is rooted in — but its bridge-candidacy gate (`if (nodeToUnit.has(bridgeNodeId)) continue`) requires the target to have ZERO existing units, which the evidenced collision shape (`Component`/`Response`, both real `@Entity` classes with existing units) structurally cannot satisfy — so the fixed mechanism's exact evidenced shape cannot reach this path. A theoretically-reachable variant (a bare-name collision landing on a genuinely zero-unit interface that is itself `implements`-ed elsewhere by a real persistence/messaging unit) has not been reproduced against a real repo. Needs its own real-evidence pass before scoping a fix, per this project's own discipline — do not extend the collision check here speculatively. |
| **Bulk residual-decision authoring** | The residual-review UI suggests answering once and applying the decision to a whole class of similar residuals, but no such batch mechanism exists — every residual currently needs its own individually-authored decision record. At real scale this is a real throughput problem (tens of near-identical residuals from a single module in one real dry run). |
| **Plain-interface bridge detection** | Interface classes with no framework marker at all (no route annotation, no persistence annotation, no security annotation) are structurally invisible even when they sit exactly on a real service boundary. Candidate mechanism: promote a plain interface to a placeholder unit when it's a field-injected dependency of an already-typed service — needs its own evidence pass before building. |
| **Graded fact admission (dual-unit gate)** | `graphify-reconciler.ts`'s `if (!from \|\| !to) continue;` drops an edge whose endpoint doesn't resolve to a TypedUnit. The dual-unit rule is a recorded product decision (`Claim_Register.md`), not a defect — but a real edge with one unresolved endpoint is currently silent rather than low-confidence. **E2 experiment run twice (T-P0-1, see `docs/solution/E2-graded-fact-admission-experiment.md`). Round 1 (coe-lab fixtures only): found and fixed two false-positive classes, 0 recall gain shown (fixtures too sparse to exercise it). Round 2 (real `spikes/` repos — Fineract/Bank-of-Anthos/Ghostfolio/Waltz): reverses that — 371 real facts recovered on `fineract-core` alone — but breaks 9 regression tests across three distinct architectural conflicts: (1) collides with other detectors' own "never guess, stay an honest ignored-item" invariants (outbound-HTTP, and by extension any future detector making the same choice); (2) silences the S1 completeness/silence flag without the story actually being more complete, since S1 isn't grade-aware; (3) the ~370+ extra placeholder units added to the shared unit pool ripple into unrelated consumers (deployment correlation showed a real, unexplained mis-match). Needs real design work (a reserved-territory registry, grade-aware S1, root-caused ripple effect) before a third attempt, not incremental tightening. Reverted again (`b4c4492`), both implementations preserved in git history (`89b7bd3`, `49e08b7`).** |
| **Contradiction detection between evidence sources** | Two sources asserting *different values* for the same fact currently both add weight in `confidence-scorer.ts` — contradiction raises confidence instead of lowering it. Evidenced class: a stale deployment manifest naming one datastore engine while current compose/config name another. Proposal: detect conflicting assertions, force a review status, never average. |
| **Secondary sources may introduce facts, not only corroborate** | Dependency-manifest corroboration is explicitly "never a primary detection source" — correct as a confidence rule, but it means a source that sees something the structural engines cannot is mute rather than low-confidence. Proposal: allow non-primary sources to introduce a fact at their own tier. Interacts with the trust-tier item in P3. |

| **Bean-factory / stereotype-free wiring detection** | A common real convention — components wired via `@Configuration`/`@Bean` factory methods with no class-level stereotype annotation on the implementation — produces zero detection signal today. Generic `@Service`/`@Component` stereotype detection and DI-based interface-to-implementation resolution are both real, related gaps. |

| **Isolated-node completeness flag (`S6`)** | No check today flags a node with zero real architecture relationships (a node that exists but connects to nothing). Not a schema-validity question — CALM's schema has no concept of it, and `calm validate` can't check it. Same mechanism class as `S1`/`S2`/`S5` in `coverage-report.ts`, at finer grain: per-node rather than per-run. **Must exclude the synthetic `system`-node `composed-of` edge from the "has a relationship" count** (`system-node-builder.ts`) — that edge is structural bookkeeping, not evidence the node participates in any real architecture, and including it would make the flag pass on almost every node in almost every run. Verified compatible with the `lib-fintech-common` must-not-detect trap: that trap resolves by emitting zero nodes, not a lone one. Naming: use `S6`, not "orphan" — that term is already the Decision-Record/Override term for a stale target reference (`override-applier.ts`); reusing it would create ambiguity. **Open question, not yet decided:** soft flag by default (reviewer decides, same posture as S1/S2/S5) with an optional `--strict-isolated-nodes`-style gate (precedent: `--strict-detect`), or a hard gate from the start — lean soft, since a lone node is sometimes honestly correct (a newly-detected unit whose relationships haven't been recovered yet) and hard-failing would punish partial detection rather than reward it. |

## P3 — Platform

| Item | Description |
|---|---|
| **Portable, CALM-round-trippable IR** | The current human-readable architecture summary is one-way (facts → markdown). A portable version that round-trips real CALM node/relationship fragments would let it double as a distribution format — proposed, needs review before implementation. |
| **Third-party plugin discovery / embed API** | The module boundary (contract version, module registry) exists; external plugin discovery and a library embed API do not. |
| **Two-tier (global + domain) mapping configuration** | Not yet built. |
| **Additional engines on measured gaps only** | Static-analysis engines beyond the current pair should only be added where a real, measured coverage gap justifies it — not speculatively. |
| **Per-(engine, fact-type) trust tiers** | `engine-capability-matrix.yml` routes per (language, framework) and is load-and-log only. Proposal: extend to an evidence-earned trust ranking *per fact type*, so an engine can be primary for one fact class and unranked for another, with the ranking changing as measurements accumulate rather than being config-declared. Prerequisite for adding any engine as a genuine second source. |
| **Probabilistic, independence-aware confidence combination** | `confidence-scorer.ts` sums evidence weights and caps at 100, which treats two dependent signals as independent and has no ceiling semantics. Proposal: probabilistic-OR combination capped below certainty. **Gate on evidence that it changes at least one real decision** — otherwise it is theory. |
| **Fact identity, incremental merge, and review history** | Every run rebuilds facts; Decision Records persist human corrections across runs but individual facts carry no stable identity or status history. Proposal: content-derived identity from semantic coordinates (never file:line, which moves), merge against prior state, and retain who/when/on-what-evidence a status changed. Enables continuous construction and auditability. **Contract change — see `Contract_Evolution_Policy.md`; bumping the contract silently skips any module whose declared major version wasn't bumped with it.** |
| **Cross-repo relationship resolution (beyond co-scanned roots)** | Multi-root covers repos scanned together. Repos *not* co-scanned have no join path. Proposal: a small per-repo manifest declaring the repo's own node ids and published contracts, resolved in strict reliability order (shared API spec identity → published artifact coordinates → service-catalogue/DNS → human review). Never infer a cross-repo edge from naming alone. |
| **Emission-coverage reporting as a governed rule** | `coverage`/`unmapped` reports exist; the rule that a fact silently lost at emission is a defect is not stated as a contract. Proposal: make "what the representation could not carry, and why" a required emission output, so representation portability becomes a measurable number rather than an assertion. |
| **Reviewer-assistance layer (advisory, off the generation path)** | `hitl-review-trigger.ts` produces a review queue; nothing helps a human *resolve* a queued item. Proposal: an advisory layer that explains evidence, proposes hypotheses for flagged unknowns, and drafts catalogue-rule candidates — **never writing facts**, consistent with `OOS-llm-core-path`, which is a permanent non-goal with revisit trigger "Never". Candidate facts surface only in the review queue; on acceptance they are recorded as the human's claim. |
| **Scope-limitations ↔ claim-register consistency** | Ongoing discipline: every new detection gap named in generated-output metadata should have a matching completeness-claim entry, checked each time scope changes. |
